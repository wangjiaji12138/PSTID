# 硬分配后性能下降的原因：预测被限制为有限模板

本次检查当前 `encoded_only_v1 + hard_st_argmax_v1` 结构与重庆 seed=88 的已训练 checkpoint。没有修改模型或重新训练。原始数据见 [hard_cq.json](hard_cq.json)，复现脚本为 [diagnose_hard_cq.py](diagnose_hard_cq.py)。

## 1. 结构上确定存在的限制

对一个样本的一个节点，两个硬分配分支分别返回原型表中一个固定向量：

```text
r_s = P_s[k_s]
r_t = P_t[k_t]
prediction = Decoder(OutputProjection(P_s[k_s] + P_t[k_t]))
```

原始历史值、节点身份、日内时间和星期均不直连预测主干；它们只影响两个原型编号。当前 Decoder 的 Conv2d 均为共享的 1×1 运算，不引入额外节点信息；内部时间维度也是同一个编码表示的广播。因此在固定权重、eval 模式下，整个模型最多产生 `K_s × K_t` 条不同的预测曲线。

默认 `K_s=16`、`K_t=8`，意味着所有节点、所有测试样本只能从最多 **128 条固定的 24 步预测曲线**中选择。原型向量即使是 64 维，也不会改变这个数量上限。原型编号不变时，历史幅值、趋势或时间身份的变化不会改变预测。训练时 Dropout 带来的随机扰动不增加推理时的表达能力。

软分配的连续权重原本还能承载输入变化；无旁路且硬分配后，这一连续信息也被丢掉。历史进入了编码器，却只通过两个离散编号传到预测端。

## 3. 原型使用集中存在，但不能简单称为全面塌缩

- 16 个空间原型中有 4 个未被使用，8 个时间原型中有 1 个未被使用。
- 最常见组合占测试样本-节点对的约 48.15%。
- 该组合对应的真实 24 步需求均值中位数为 0，90% 分位数约为 0.0417；其预测均值约为 0.00091。

因此，大量样本进入同一组合与零需求数据有关，不能仅凭占比高就认定训练完全塌缩。实际还使用了 81 种组合。即使全部 128 种组合都被使用，有限模板限制仍然存在。

时间温度从 0.5 学到约 0.42885。训练损失从约 1.7248 降到约 0.9039，不能把现象归因为所有梯度都断掉。直通估计只是让分配网络能够获得代理梯度，并不能恢复硬选择丢掉的连续表示，也不保证容易优化。

## 4. 对后续结构选择的含义

“硬分配”与“无旁路”组合本身不必导致只能输出有限模板；造成该限制的是**选中的对象是固定输出向量，并且该向量是预测端的全部输入**。

若继续坚持硬选择且不允许绕过原型，一种不同的结构方向是让原型决定处理历史的变换或专家：

```text
历史表示 h → 硬选择原型 k → 由所选原型定义的变换 T_k(h) → 预测
```

这里所有历史信息仍必须经过所选原型控制的运算，但在同一个 k 下，输出也可以随 h 连续变化。这已经改变了原型的角色，需要明确设计和重新验证，不能声称一定改善精度。本次没有实施该结构变更。

## 复现

在项目根目录运行：

```bash
PYTHONPATH=. python docs/prototype_diagnosis/diagnose_hard_cq.py
```

脚本读取两个指定实验及数据集，使用 CPU 推理，写入 `hard_cq.json`，不更新 checkpoint。上述诊断只覆盖该数据集和随机种子；有限模板上限则直接来自当前模型结构。
